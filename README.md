# ai-log-incident-analyzer-go

A Go port of [ai-log-incident-analyzer](https://github.com/sopabarth/ai-log-incident-analyzer):
a service that takes raw, messy error logs / stack traces and turns them into
structured, prioritized incidents (category, root cause, priority, confidence,
`needs_human_review`), with Postgres-backed dedup so a burst of identical
errors doesn't call the LLM hundreds of times.

The goal is a faithful port of the Python service, built one piece at a time.
It is a standalone project with its own database and migrations; it does not
share anything with the Python service at runtime.

## Layout

```
internal/
  domain/    enums.go     enums + ParseEnvironment
             request.go   RawLogEntry (lenient environment/timestamp parsing)
             analysis.go  LLM result types, Validate methods, Parse* functions
             record.go    IncidentRecord (the API response)
             (the equivalent of app/schemas.py - Go has no Pydantic, so
             required fields, ranges and enum membership are checked explicitly)
  parser/    raw log normalization + SHA-256 dedup hash (app/parser.py)
  config/    settings from environment variables
  store/     Postgres access: create incidents, record duplicates, run migrations
migrations/ goose SQL migrations, embedded into the binary
cmd/
  migrate/   migrate [up|down|status] - the equivalent of `alembic upgrade head`
```

## Parity with the Python implementation

`internal/parser` is written the Go way (`strings.Lines`, `strings.TrimSpace`,
`unicode.IsSpace`, a plain `\s` regexp) rather than re-implementing Python's
string semantics. For ordinary logs the result is the same anyway, and it is
tested against **golden output generated by the Python parser**
(`internal/parser/testdata/golden.json`, produced by `gen_golden.py` from the
Python repo): the 41 synthetic logs plus edge cases (CRLF, truncation, empty
input, Unicode text...). Same normalized text means the same SHA-256, so a
given error hashes identically in both services and the Go parser's behaviour
stays checked against the original.

The one known gap: Python treats a few more characters as whitespace/line
breaks than Go does (form feed, NEL, `\x1c`-`\x1f`, a lone `\r`). A log
containing those can normalize - and hash - differently in the two services.
It does not occur in real application logs, so it is accepted rather than
emulated.

`domain` keeps the request/response contract of the Python API, and is
otherwise written in plain Go:

- `environment` is matched case-insensitively and accepts `development` and
  `production` as long forms of `dev` and `prod`. (The Python enum is a bit
  stricter - it rejects `"PROD"` - which is not worth reproducing.)
- `timestamp` accepts offset-less datetimes (read as UTC) and plain dates.
- All request / LLM-result fields are required (an empty string is fine, a
  missing key is not); `root_cause_summary` is capped at 300 and
  `priority_reasoning` at 200 *characters*; `confidence` must be in `[0, 1]`.
- `IncidentAnalysis` embeds `ClassificationResult` and `PriorityResult`, so
  the two decomposed LLM steps compose directly and the JSON stays flat.

## Database and dedup

Postgres 18, schema managed by embedded [goose](https://github.com/pressly/goose)
migrations (`migrations/`). The schema keeps the Python project's design -
native enums for `environment` and `priority` (closed sets), a `CHECK`
constraint for `category` (the taxonomy that may grow, and the one that is
painful to evolve as a native enum), a UUID primary key.

Dedup is one SQL statement, `Store.RecordDuplicate`: find the incident with this
hash that was last seen within the window **and** bump its counter in a single
`UPDATE`. Compared with a read-then-write this makes concurrent duplicates count
exactly once each (tested with 50 goroutines), and the window is evaluated with
the database's `now()` so app and database clocks cannot disagree. The window
slides - every duplicate refreshes `last_seen_at` - and a composite index on
`(raw_text_hash, last_seen_at DESC)` serves the lookup.

Known gap, same as the Python service: two *first* occurrences of a brand-new
error arriving at the same instant both miss and both create an incident.

## Development

```bash
docker compose up -d --wait db      # Postgres on localhost:5433 (the Python project uses 5432)
cp .env.example .env                # DATABASE_URL, DEDUP_WINDOW_MINUTES
go run ./cmd/migrate up             # apply migrations (also: down, status)
```

Tests. Database tests are skipped unless `TEST_DATABASE_URL` is set; each one runs
in its own throwaway schema, so they can run against the dev database:

```bash
go test ./...                      # everything that needs no database
TEST_DATABASE_URL='postgres://root:root@localhost:5433/incident_analyzer?sslmode=disable' go test ./...
```

Regenerating the golden parser data (needs the Python repo checked out):

```bash
cd ../ai-log-incident-analyzer
PYTHONPATH=. uv run python <this repo>/internal/parser/testdata/gen_golden.py \
    <this repo>/internal/parser/testdata/golden.json
```
